# M9 - 루빅스 큐브 칸 색 상태와 층 회전
## 개요
면마다 색을 가진 루빅스 큐브에서 한 층을 돌릴 수 있는 상태를 만들었다.
- 칸 54개의 색을 면마다 3×3 `char` 배열로 저장하고, 렌더링할 때 삼각형 번호로 칸을 찾아 그 칸의 색으로 칠한다. (결정 기록: M9 루빅스 큐브 상태 저장과 회전 구현 방식)
- 칸 번호 기준(전개도)을 정하고, 그 기준에 맞춰 정점·인덱스 버퍼를 다시 만들었다.
- U, D, F, B, L, R의 시계방향 90도 회전을 함수로 구현하고 키에 배정했다. 회전 애니메이션은 넣지 않고 색만 바꾼다.
- 라인 인덱스 버퍼로 칸 경계선을 그렸다.

## 소스 코드
`RubiksCube/CubeLogic.h`, `RubiksCube/CubeMain.cpp`, `RubiksCube/RubiksCubeMesh.h`

## 1. 설계
### 상태 저장
- 상태의 단위는 칸 하나하나의 색이다. 하얀색이면 `'W'`, 파란색이면 `'B'`처럼 `char`로 저장하고, 면마다 3×3 구조로 둔다.
- 인덱스 버퍼는 고정해 두고 "이 삼각형은 몇 번 칸"을 찾는 데만 쓴다. 색은 별도의 배열에 둔다.
- 이유: 색을 회전시키는 로직을 렌더링과 분리하기 위해서다. `char`는 메모리를 최대한 줄이기 위해 썼다.

### 한 면을 돌리면 움직이는 칸
- 한 면을 돌리면 그 면의 9칸만 바뀌는 것이 아니라, 같은 층에 있는 다른 면들도 영향을 받는다.
- 회전하는 면은 가운데를 제외한 8칸의 위치가 바뀐다.
- 인접한 4개 면에서는 회전하는 면과 맞닿은 행 또는 열의 3칸이 다음 면으로 옮겨 간다.

### 칸 번호 기준 (전개도)
```
   5
0  2  1  3
   4
```
- 면 번호는 정점 버퍼의 면 순서(0: z = −1, 1: z = +1, 2: x = −1, 3: x = +1, 4: y = −1, 5: y = +1)이고, 2번 면이 F다.
- 각 면을 전개도에서 바깥에서 본 상태로 0번 칸을 왼쪽 위에 두고, 0 → 1 → 2 가로 방향으로 번호를 붙인다. 3×3 구조를 쓸 때 자연스럽기 때문이다.
- 이 기준으로 F 회전을 추적해 보면, 인접 면으로 옮겨 갈 때 3칸의 인덱스 순서가 뒤집히기도 한다.
  - 0번 면 (2, 5, 8) → 5번 면 (8, 7, 6) → 1번 면 (6, 3, 0) → 4번 면 (0, 1, 2)

### 시계방향 기준
- 처음에는 F를 바라보는 시점으로 시계방향을 정하려 했지만, U와 L을 돌릴 때는 방향이 다르게 보였다.
- 그 면을 직접 바라볼 때만 "이 면이 시계방향으로 회전한다"가 6개 면 모두에 같은 규칙으로 적용된다. 그래서 회전하는 면을 정면으로 바라보는 시점으로 정했다.
- 이 기준에서 B를 시계방향으로 돌리면 F 쪽에서는 반시계방향으로 보인다.
- 가운데 층은 넘어가고, U, D, F, B, L, R의 시계방향 90도 회전만 구현했다.

### 회전 구현 방식
- 회전마다 함수를 두고, 함수 안에서 각 칸의 이동을 직접 지정한다.
- 회전하는 면 자신의 8칸 이동은 모든 면이 같은 알고리즘을 쓴다. 인접 면의 이동은 경우마다 많이 달라서 따로 작성한다.
- 값을 옮기면 옮겨 간 자리의 원래 값이 사라진다. 그래서 옮기기 전에 값을 임시로 빼 두었다가 각각 대입한다.
- 진행 순서는 F 구현 → 4번 회전 테스트 → F에서 먼 면 하나 구현 → 두 함수 비교로 잡았다. *(Claude 추천 플로우)*
- 검증: 같은 회전을 4번 수행하면 원래대로 돌아와야 한다.

## 2. 정점·인덱스 버퍼 통일
- 기존 정점 좌표는 M7에서 Claude가 생성한 것이라 칸 번호 기준과 맞지 않았다. 칸 번호 기준에 맞춰 `RubiksCubeMesh.h`를 다시 생성하도록 요청했다.
- 면 f의 정점은 `f*16 + r*4 + k`(r: 위 → 아래 행, k: 왼쪽 → 오른쪽 열)이고, 면 f의 c번 칸은 `rubiksIndexBuffer[f*18 + c*2]`, `[f*18 + c*2 + 1]` 두 삼각형이다.
- 감김 방향은 기존 백페이스 컬링 규칙을 그대로 유지했다. 화면에서 면 색 배치와 컬링이 이전과 똑같이 보이는 것을 확인했다.

## 3. 회전 구현
### 면 상태
```cpp
enum ESurface
{
	Left,
	Right,
	Front,
	Back,
	Down,
	Up
};

char L_arr[3][3] = { {'O', 'O', 'O'},
					 {'O', 'O', 'O'},
					 {'O', 'O', 'O'} };
// R_arr('R'), F_arr('G'), B_arr('B'), D_arr('Y'), U_arr('W')도 같은 형태
```
- `ESurface`의 순서는 메시의 면 번호 0~5와 같다 (L, R, F, B, D, U).

### 회전하는 면 자신
```cpp
void SurfaceClockwise(char (*arr)[3])
{
	char tmp[3][3] = { {arr[2][0], arr[1][0], arr[0][0]},
					   {arr[2][1], arr[1][1], arr[0][1]},
					   {arr[2][2], arr[1][2], arr[0][2]} };
	memcpy(arr, tmp, sizeof(tmp));
	return;
}
```
- 6개 회전 함수가 모두 이 함수로 자기 면을 돌린다.

### 인접 면 (F 예시)
```cpp
void F_Clockwise()
{
	SurfaceClockwise(F_arr);

	char L_tmp[3] = { L_arr[0][2], L_arr[1][2], L_arr[2][2] };
	char U_tmp[3] = { U_arr[2][0], U_arr[2][1], U_arr[2][2] };
	char R_tmp[3] = { R_arr[0][0], R_arr[1][0], R_arr[2][0] };
	char D_tmp[3] = { D_arr[0][0], D_arr[0][1], D_arr[0][2] };

	for (int i = 0; i < 3; i++)
	{
		L_arr[i][2] = D_tmp[i];
		U_arr[2][i] = L_tmp[2-i];
		R_arr[i][0] = U_tmp[i];
		D_arr[0][i] = R_tmp[2-i];
	}
	return;
}
```
- 인접 면 4개의 3칸을 먼저 임시 배열에 저장한 뒤 대입한다. 인덱스 순서가 뒤집히는 곳은 `2-i`로 읽는다.
- 식 오류를 고친 뒤 F와 L을 구현했다. 오류는 대부분 어떤 인덱스를 넣느냐의 문제였다. 예를 들어 `R_arr[0][i] = B_tmp[2-i];`로 써야 할 곳을 `R_arr[0][i] = B_tmp[i];`로 작성하는 식이었다.
- F와 L을 비교한 뒤 표로 분리하지 않고 함수 방식을 유지했다. 현재 인덱스에서는 U와 D의 칸이 다른 면의 칸과 대응되는 방식이 회전마다 달라서, 식을 직관적으로 쓰기 위해서다.
- 나머지 R, B, U, D도 같은 방식으로 구현하고, `WM_KEYDOWN`에서 L, R, F, B, U, D 키에 각각 배정했다.

### 렌더링: 삼각형 → 칸 → 색
```cpp
int surfaceNum = i / 18;
int faceNum = (i % 18) / 2;

switch(surfaceNum)
{
	case Left:
		color = L_arr[faceNum / 3][faceNum % 3];
		break;
	// Right, Front, Back, Down, Up도 같은 형태
}

switch (color)
{
	case 'O':
		graphics.FillPolygon(&orangeBrush, points, 3);
		break;
	// 'R', 'G', 'B', 'Y', 'W'도 같은 형태
}
```
- 삼각형 번호 i로 면 번호(`i / 18`)와 칸 번호(`(i % 18) / 2`)를 구하고, 그 면 배열에서 색 문자를 꺼내 브러시를 고른다.

### 검증
- 같은 회전을 4번 수행하면 원래대로 돌아오는지로 확인했다.
- *Claude 시뮬레이션*: 6개 함수 모두 54칸 전부가 실제 큐브의 층 회전 결과와 일치했다. 같은 회전을 4번 하면 원래 상태로 돌아왔고, `R U R' U'`를 6번 반복하거나 무작위로 40번 섞은 뒤 역순으로 되돌려도 원래 상태로 돌아왔다. 섞은 뒤에도 각 색은 정확히 9칸씩이었다. (반시계 회전은 같은 함수를 3번 호출하는 것으로 대신했다.)

## 4. 칸 경계선
```cpp
for (int i = 0; i < 6; i++)
{
	if (isRenderTarget[i * 18] == true)
	{
		for (int j = i * 8; j < (i + 1) * 8; j++)
		{
			graphics.DrawLine(&blackPen,
				main_pixel_buffer[rubiksLineIndexBuffer[j](0)](0), main_pixel_buffer[rubiksLineIndexBuffer[j](0)](1),
				main_pixel_buffer[rubiksLineIndexBuffer[j](1)](0), main_pixel_buffer[rubiksLineIndexBuffer[j](1)](1));
		}
	}
}
```
- 경계선용 라인 인덱스 버퍼 `rubiksLineIndexBuffer`는 요청해서 Claude가 생성했다. 원소 하나가 선분의 양 끝 정점 인덱스이고, 면 하나에 가로선 4개와 세로선 4개, 모두 48개다. 면 f의 선은 `f*8` ~ `f*8 + 7`이다.
- 뷰 공간에서 렌더 여부를 따질 때 그리지 않는 칸이 하나 생긴다는 것은 그 면을 전부 그리지 않는다는 뜻이다. 그래서 면 단위로 렌더 여부를 따지고, 렌더링 대상인 면만 선을 그린다.
- `isRenderTarget[i * 18]`을 면의 대표값으로 쓰고, 면을 모두 칠한 뒤에 선을 그린다.

## 5. 디버깅 기록
- **`CubeLogic.h`의 함수로 중단점이 넘어가지 않음**: RubiksCube 프로젝트의 Debug|x64 구성이 실제로는 최적화 빌드로 설정되어 있었다(`UseDebugLibraries` false, `WholeProgramOptimization` true, 전처리기 `NDEBUG`, 최적화 항목 기본값). VS 프로젝트 속성에서 직접 고쳤다.
  - *Claude 설명*: 최적화 빌드에서는 작은 함수가 호출하는 쪽에 인라인되어, 디버거가 그 함수 안의 줄에 중단점을 연결하지 못하고 한 단계씩 들어가기도 함수 안으로 넘어가지 않는다.
- **회전 식의 인덱스 오류**: 인접 면으로 옮길 때 넣을 인덱스(`i`와 `2-i`)를 잘못 쓴 경우가 대부분이었다. 고친 뒤 F와 L이 맞게 동작했다.
